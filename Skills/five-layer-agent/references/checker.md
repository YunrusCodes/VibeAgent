# 稽核檢查清單

拿到既有 spec 或程式碼時逐條走。輸出格式固定為：

```
[違反 <條號>] <位置>
問題：<一句話>
最小修正：<具體改法>
```

不要給泛泛的建議。**指不出位置與最小修正的，不要寫。**

## 先判斷適用性

在檢查之前先確認這套架構該不該套用：

- 所有單元都在 L0/L1？ → 傳統三層即可，只檢查引導層是否存在。不要硬套五層。
- 有任一單元達到 L2 以上？ → 全套適用。

## 機械可檢（不需要判斷，能寫成測試就寫）

> 命名注意：本表的 M1–M13（**無**連字號）是檢查項編號；`agent-composition` 的 M-1…M-3（**有**連字號）是 meta 條文。兩者無關，引用時勿混用。

| # | 檢查 | 通過條件 |
|---|---|---|
| M1 | 演算單元有無實例狀態 | 無 `self.<state>` 跨呼叫存活 |
| M2 | 演算單元能否觸及 store | 建構子與參數中無 store handle |
| M3 | 每個 `risk: high` 條目 | 有非空 `hard_check` |
| M4 | 每個不可逆邊界動作 | 有 `idempotency_key`，且在某條 `grant` 的涵蓋內 |
| M5 | `precheck` 內是否有模型呼叫 | 無 |
| M6 | 資料層介面 | 無 `update` / `delete` / `set` |
| M7 | `__refusals` / `__amendments` | 在壓縮排除清單內 |
| M8 | 子層 `grants` | ⊆ 父層 |
| M9 | 子層 `budget` | 每項 ≤ 父層 |
| M10 | 父層 `forbid` 條目 | 全部出現在子層，ID 未重新編號 |
| M11 | `depth` | 遞增且有上限 |
| M12 | 回報路徑 | 不受 `grants` 收窄影響 |
| M13 | 終止型別 | 三值，且 retry 邏輯顯式跳過 `refused` |

M8–M12 是 narrowing-only 的機械檢查。M10 只能擋住「條目被刪掉」，**擋不住「條文被改弱」**——文字層級的放寬需要人類審查，標記出來交給人。

## 需要判斷

**J1 — 互相不完整**
逐層問：這一層自己能闖出什麼禍？答案必須是「沒有」。若某一層單獨就能造成不可挽回的後果，那一刀切錯了。

**J2 — 調度層是否偷做運算**
找 `step` 裡的模型呼叫、複雜條件、啟發式評分。這些都是沒有 ID、不在追蹤裡、無法單獨評測的隱形演算單元。

**J3 — 不可逆動作的授權模式**
是 denylist 還是 allowlist？不可逆的必須是 allowlist。看到「不得刪除重要檔案」這類條文就是紅旗——「重要」沒有定義，窮舉不完。

**J4 — L3 是否直接接不可逆動作**
追每條執行路徑。L3 與 L0 不可逆動作之間必須有可驗證的 L2 或人類確認。

**J5 — 拒絕的品質**
既有的拒絕路徑有沒有引用條目 ID？有沒有 `minimal_amendment`？只回「無法完成」的，等同沒有回報通道。

**J6 — 死鎖出口**
目標與約束衝突時，系統會怎樣？如果答案是「重試」或「模型自己想辦法」，那它一定會違規。

**J7 — 棘輪**
看修法史。放寬與收緊的比例是多少？拒絕率隨版本的變化？**拒絕率歸零要當作紅旗處理，不是好消息**——可能是約束已經放寬到不會擋到任何東西。

**J8 — 過度分層**
反過來查：有沒有為了湊滿五層而生出空殼？空的邊界層、只有一個 dict 的資料層、只有一條路徑的調度層，都該塌縮。

## 常見誤判

**把「事前自審」當成「不得自審」的違反。**
調度層應該自己判斷合法性（依法行政），這是義務。禁止的是它認定自己有沒有違規——那必須由看不到它推理過程的獨立單元做。守法者 ≠ 認定者。

**把引導層當資料層。**
兩者都是文字、都進 context、在實作上走同一條路。差別是語意角色：資料是被運算的**對象**，引導是運算的**構成條件**。判準——如果拿掉它，agent 變成**做錯事**，那是引導層；變成**做錯順序**或**卡住**，那是調度層；變成**不知道**，那是資料層。

**把需要當下狀態才能判斷的規則放進引導層。**
引導層是靜態、跨呼叫、宣告式的。需要看狀態才能判斷的，下放給調度層。

**把 `failed` 當成 `refused` 的同義詞。**
budget 耗盡、API 逾時、工具錯誤都是 `failed`，可以重試。只有規範性衝突才是 `refused`。混用會讓重試邏輯壓迫合法的拒絕。
